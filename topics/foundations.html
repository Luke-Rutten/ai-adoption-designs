Foundations & Architecture

Overview

LLMs are fundamentally neural networks designed to predict the next token in a sequence. Tokens, as the building blocks, can be letters, a cluster of letters, or even a whole word. Under the hood, LLMs convert user inputs into tokens using a fixed vocabulary bank (e.g., "Through thick and" --> ['Th' + 'rough' + 'thick' + 'and']), and the output is a probability distribution for which token is likely to appear next (e.g., ['thin' = 0.8, 'thicker' = 0.2]).

There are billions of node connections in these neural networks, and each input token is processed independently in light of the other tokens around it. This is what we call the context.

Key implication: A model only knows what is in its context. It has no memory of prior chats outside the tokens it is fed. In order for a model to have "memory," this must be reinjected into the input.

The core model loop

The entire context window (system, chat history, new input) is processed all at once every single time.

Key implication: A long chat, even with small, simple prompts, gets expensive quickly because it reprocesses the whole chat on each new message.

Randomness is both a great strength and a great weakness of AI. It's what allows it to be flexible, and also what sometimes causes it to go off the rails. This randomness is controlled by what we refer to as temperature. Temperature controls how random the probability distribution selection is — 0 to 0.3 is generally preferred for consistent tasks, while 0.7 to 1 is preferred for more creative tasks. But even 0 is non-deterministic, due to floating point numbers and rounding.

Note: why does it feel like LLMs are good at code? Correctly written code follows rigid semantic rules — there's a single correct way to write syntax. That makes the token pattern a much clearer signal that's more reliable to replicate.

Skills

Skills exist to solve a specific tension. Some context — a workflow, a reference, a set of instructions — is needed sometimes, but not every single turn. Including it all the time bloats context: it's expensive, and it's confusing for LLMs to handle when the prompt is full of material that's irrelevant to the task at hand. But leaving it out entirely is also bad — it means re-typing or re-explaining the same thing every time it's actually needed. A skill is reusable, shareable context that loads only when it's relevant, avoiding both problems at once.

Key concept: progressive disclosure. Progressive disclosure is the notion that not all context should be available in every single prompt. Rather, sometimes it should be included and sometimes it should be left out. AI systems use descriptions as short-context cues for when further information should be loaded into context; otherwise, it's left out.

Skills leverage progressive disclosure to load context into the context window only when relevant. A skill has a description — a short set of words that tells the LLM what the skill does and when it should be activated — but hides the rest of the text behind the skill itself. If the LLM determines the skill is relevant, based on its description and the rest of the context it has, it loads the rest of the skill text into its context window, basically as if the user had just given it all of the context contained within the skill.

In this manner, we're able to leverage reusable context in the form of the skill, but only add it into our context window — which is expensive, and can confuse the LLM if there's too much — when it's relevant to the conversation.

Mechanically, there's nothing special going on here — it's all just next-token generation, same as everything else in the core model loop above. Every skill's name and description is always part of the system prompt, every single turn. If the model judges a skill relevant to what the user is asking, it generates a tool call to load that skill, and the skill's body text comes back into context as the result of that tool call — exactly like any other tool result. Nothing about this is a separate mechanism from tool use; it's tool use, applied to loading text.

This has a key implication: since the description is what the model reasons over to decide whether to load the skill, and it's always in context, that description should be short, specific, and should read like an activation instruction — something close to "use this skill when <specific situation>" — rather than a vague summary of what the skill contains.

always loaded 
---
name: pdf-forms
description: Fills out and extracts data from PDF form fields. Use when the user mentions a PDF, a form, or asks to fill in or read form fields.
---
loaded only when relevant 
# Filling a PDF form

1. Inspect the form fields: `pdftk input.pdf dump_data_fields`
2. Map each field name to a value
3. Fill the form: `pdftk input.pdf fill_form data.fdf output filled.pdf`

This carries a few implications for how skills should be constructed. The first is the scope of the skill, and of its description. There's an inherent trade-off: go too broad, and it activates so often that it doesn't actually narrow the context — it might as well just be always loaded. Go too narrow, and it doesn't activate when it should, and doesn't add any value.

Skills actually have a third layer to them — three stages of activation:

  • Always: the name and description.
  • When relevant: the skill body text.
  • When extra stuff is needed: extra files.

That third layer doesn't load automatically just because the skill activated. Extra files aren't pulled into context when the skill body loads — they're reached the same way everything else is reached, through further next-token generation. The skill body has to specifically reference a file by name or path for the model to know it exists and decide to go get it. A skill can activate and still never touch its extra files, if nothing in the body text points the model toward them.

Across the industry, extra files tend to fall into three categories, though a skill isn't limited to these:

  • Scripts: blocks of code — Python, shell, anything executable — that are never loaded into context themselves. Instead, the model generates a tool call to run the script, and only the script's output comes back into context, the same way any other tool result does.
  • References: plain text or documents that do get loaded into context when the model reads them — extra information that's useful but too long or too specific to put in the skill body itself.
  • Assets: files a script might operate on, or that get copied or handed off somewhere, rather than read. The model typically only ever sees the asset's path, not its contents — it's something other tools act on, not something the model reads.

Semantic activation can also be bypassed entirely: typing a skill's name directly (e.g. /skill-name) forces it to load, regardless of whether its description would otherwise have matched. But loading is all that guarantees — a skill entering context guarantees only that its text has been read by the model, not that the model acts on it. What happens next is still just generation.

Tools

Tools are what allow LLMs to interact with external systems.

Fundamentally, LLMs are next-token generators. That's all they do — produce tokens, one at a time. Tokens, as text, don't directly produce action; an LLM on its own can't send an email, read a file, or run a search, no matter how clearly it describes the intent to do so. Getting from text to action requires a second step, something that sits outside the model and turns generated text into a real effect in the world.

This is where tools come in.

Tools are systems designed to accept text in a specific format and then execute some action based on that text. So, for example:

model generates 
{
  "tool": "get_weather",
  "input": { "city": "Seattle" }
}
tool returns 
{
  "temp_f": 58,
  "conditions": "light rain"
}
// this result is inserted back into the model's context
// before it continues generating

This means the tool framework is responsible for doing anything other than outputting text, and can be a great point of control for what the system can or cannot do. The model only ever generates the text. The tool is what actually goes out and does things, then returns information back to the model.

This doesn't come for free, however — tool descriptions, tool processing, and whatever the tool returns all become part of the context.

Tool descriptions enter the system prompt much the same way skill descriptions do — always present, telling the model what each tool does and when to reach for it. Some of the most basic tools, like code execution for certain models, skip that step entirely and get trained into the model itself rather than described at request time. Tools typically also carry a schema: a definition of exactly what shape the tool call's input has to take — which fields are required, what type each one is — so the model's output can actually be parsed and acted on, not just loosely interpreted.

Getting from generated text to an executed action depends on activation: some models emit special signal tokens that mark where a tool call begins and where it ends, so the surrounding system knows which span of output to treat as a tool call rather than as a reply to the user. Those spans are typically flagged separately from ordinary user-facing text, which is how an application like Claude Code knows to hide the raw tool call from the person watching, and instead hand its contents off to whatever framework actually executes it. Middleware often sits at that handoff point, checking that the emitted tool call actually matches its schema before anything downstream tries to run it.

Agents

At a high level, agents are mostly taken care of for you. A plain LLM call is just a single round of next-token generation: you send a prompt, it generates tokens, and those tokens come back to you as a string of text. That's the whole interaction. On its own, a single call can't iterate — it can't generate a tool call, get that tool call executed, see the result, and decide what to do next. There's no loop, no automated goal-directed behavior, just one prompt, one response.

An agent is what adds that loop: multi-step, goal-directed, iterative processing, where the model's own output at each step feeds back in to decide the next one. Building that loop is real architecture — deciding when to stop, how to feed tool results back in, how to handle errors — but it's not something you typically need to design yourself. Mainline harnesses like Claude Code or Cursor already handle the agent loop for you.

What's actually useful to understand, day to day, is subagents — because those are something you configure.

A subagent works a lot like a skill. It has a description that's always loaded into the system prompt, every turn. The model can generate a tool call to activate it when the description looks relevant, and once activated, the subagent's own body text — the instructions for what it does — loads in as context, the same way a skill's body does.

Where a subagent differs from a skill is in a few specific ways:

  • It runs in its own context window. Activating a subagent doesn't load its text into the main conversation's context — it spins up a separate context window entirely. That window typically starts with a system prompt of its own, a delegation prompt from whatever decided the subagent was needed (a summary of the task to do), and the subagent's body text. It then runs its own loop, independently, outside the main chat UI, until it reaches a conclusion. At that point it sends a summary of what it did and learned back to the main conversation, which shows up there as a single tool call result.
  • It can run on a different model. The main conversation might run on a large, expensive model, while a subagent doing quick, mechanical work — reading a file, running a lookup — runs on something cheaper.
  • It can be limited to a subset of tools. A subagent can be restricted so it only has, say, a read-only tool — not just discouraged from writing anywhere, but structurally unable to, even if the model "wanted" to.
  • It can have specific skills forced into context. You can specify skills that always load with a given subagent, rather than relying on semantic activation.

This unlocks context isolation, in both directions. The main conversation doesn't get clogged up with everything the subagent did along the way — every tool call, every edit, every dead end it troubleshot — only the final summary. And the subagent doesn't have to carry the main conversation's entire history into its own context either; it can start clean and do its own processing without re-reading everything that came before.

There are three ways a skill ends up available inside a subagent's context:

  • Standard, global availability. Any skill that's globally available is also available to the subagent, and can activate for it the same way it would in the main conversation.
  • Forced in the subagent's front matter. Listing a skill in the subagent's configuration guarantees its full body text is loaded into the subagent's context from the moment it starts, with no activation step needed.
  • Scoped to the subagent only. A reference or asset file placed inside the subagent's own folder, with explicit instructions for when to read it and where to find it, is reachable only from that subagent — it never activates for the main conversation or any other subagent, but it still activates conditionally rather than always loading.

MCPs

MCP stands for Model Context Protocol. It exists to standardize how models connect to external services, so that connection and maintenance work doesn't have to be duplicated. Without it, every LLM-facing harness (Claude Code, Cursor, …) that wants to talk to every external service (GitHub, Google Drive, …) would need its own bespoke integration — an N×M problem. MCP collapses that: one MCP server gets built for a given service, and any MCP-compatible client can connect to it the same standardized way. Re-implementation drops out, and ongoing maintenance stays in one place.

An MCP server is, underneath it all, just code — written against an MCP SDK, running locally or in the cloud. That means a developer can put whatever else they want in front of the actual integration logic, and in practice the server often ends up acting as middleware: logging, security checks, authentication, input validation, all of it can sit inside the server before a request ever reaches the thing it's integrating with.

An MCP server can expose three kinds of things to an LLM: tools, resources, and prompts.

Tools

MCP tools work like any other tool — they get loaded into the context window automatically once the connection handshake completes, the same as a tool installed locally. The one wrinkle is scale: if a server exposes so many tools that they'd eat up too much context, they get hidden behind a tool-search tool instead. That search tool uses pattern matching to dynamically pull in just the names and descriptions of whichever tools actually look relevant, only once the model decides it needs something it doesn't currently have loaded.

Resources

Resources are pieces of context made available on demand — read with a resource-read tool, or discovered with a resource-list tool. By default, a resource itself isn't loaded into context automatically the way a tool description is; the LLM only sees the read and list tools, and has to decide to go use them before a given resource's content ever shows up in context.

Prompts

Prompts are pre-built prompt templates the MCP server offers, but unlike tools and resources, they're user-activated rather than model-activated. When a user wants to use one, and the harness supports MCP prompts (most common ones do), it surfaces some kind of menu — options, fields, questions — for the user to fill in. Once the user has answered, those question-and-answer pairs get inserted into the context window as if the user had just typed them out directly. It's a way of structuring exactly what information a user needs to supply, without the model having to infer or request it turn by turn.

Workflows

Real processes often need both determinism and flexibility, at different points. LLMs alone don't handle determinism well — ask the same thing twice and you can get two different answers. Deterministic systems alone don't handle flexibility well — they only do exactly what they were coded to do. A workflow is what lets a single process lean on determinism where it needs reliability, and lean on an agentic, flexible step where it needs judgment — within the same pipeline.

Each step in a workflow needs something to actually do the work, and often something else to check that work before it moves on — an executor and an approver. Either role, at any given step, can be filled by an LLM, by plain code, or by a human, and each choice trades off differently:

Workflows tend to follow a handful of recurring patterns:

  • Sequential: steps run one after another, in a fixed order.
  • Concurrent: multiple steps run at the same time, independently of each other.
  • Handoff: steps still run one after another, but which step comes next depends on the task — the order itself isn't fixed.
  • Coordination: multiple agents collaborate synchronously toward one shared recommendation or output.
  • Evaluator-optimizer loop: a step's output gets evaluated against some criteria, and redone if it doesn't pass, looping until it does.
  • Human-in-the-loop checkpoint: the process pauses entirely and waits for a human to approve before it continues.

These patterns are often just implemented directly in code. There are also workflow orchestrators — LangGraph, for example — that provide a lot of this structure (steps, branching, loops, state) out of the box, rather than building it from scratch.

Key implication: almost any loop in a workflow — an evaluator-optimizer loop especially — needs a hard cap on iterations. Without one, a step that never quite satisfies its own evaluation criteria will simply loop forever.

Context

Context lies at the core of every LLM output. It's the piece that actually gets processed. It's what determines the available skills, tools, agents, and information. It's how costs are calculated. Ultimately, context is at the center of almost everything LLMs do.

Following this, managing context is of critical importance. Consequently, it gets an entire section in this repository.
