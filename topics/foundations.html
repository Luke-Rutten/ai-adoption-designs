Foundations & Architecture

Overview

LLMs are fundamentally neural networks designed to predict the next token in a sequence. Tokens, as the building blocks, can be letters, a cluster of letters, or even a whole word. Under the hood, LLMs convert user inputs into tokens using a fixed vocabulary bank (e.g., "Through thick and" --> ['Th' + 'rough' + 'thick' + 'and']), and the output is a probability distribution for which token is likely to appear next (e.g., ['thin' = 0.8, 'thicker' = 0.2]).

There are billions of node connections in these neural networks, and each input token is processed independently in light of the other tokens around it. This is what we call the context.

Key implication: a model only knows what is in its context. It has no memory of prior chats outside the tokens it is fed. In order for a model to have "memory," this must be reinjected into the input.

The core model loop

The entire context window (system, chat history, new input) is processed all at once every single time.

Key implication: a long chat, even with small, simple prompts, gets expensive quickly because it reprocesses the whole chat on each new message.

Randomness is both a great strength and a great weakness of AI. It's what allows it to be flexible, and also what sometimes causes it to go off the rails. This randomness is controlled by what we refer to as temperature. Temperature controls how random the probability distribution selection is — 0 to 0.3 is generally preferred for consistent tasks, while 0.7 to 1 is preferred for more creative tasks. But even 0 is non-deterministic, due to floating point numbers and rounding.

Note: why does it feel like LLMs are good at code? Correctly written code follows rigid semantic rules — there's a single correct way to write syntax. That makes the token pattern a much clearer signal that's more reliable to replicate.

Skills

Limiting context is both cost- and processing-efficient. Not all available context should be included every time — that would be expensive, and confusing for LLMs to handle. Skills are reusable context an AI can "read" into its context window when relevant.

Key concept: progressive disclosure. Progressive disclosure is the notion that not all context should be available in every single prompt. Rather, sometimes it should be included and sometimes it should be left out. AI systems use descriptions as short-context cues for when further information should be loaded into context; otherwise, it's left out.

Skills leverage progressive disclosure to load context into the context window only when relevant. A skill has a description — a short set of words that tells the LLM what the skill does and when it should be activated — but hides the rest of the text behind the skill itself. If the LLM determines the skill is relevant, based on its description and the rest of the context it has, it loads the rest of the skill text into its context window, basically as if the user had just given it all of the context contained within the skill.

In this manner, we're able to leverage reusable context in the form of the skill, but only add it into our context window — which is expensive, and can confuse the LLM if there's too much — when it's relevant to the conversation.

always loaded 
---
name: pdf-forms
description: Fills out and extracts data from PDF form fields. Use when the user mentions a PDF, a form, or asks to fill in or read form fields.
---
loaded only when relevant 
# Filling a PDF form

1. Inspect the form fields: `pdftk input.pdf dump_data_fields`
2. Map each field name to a value
3. Fill the form: `pdftk input.pdf fill_form data.fdf output filled.pdf`

This carries a few implications for how skills should be constructed. The first is the scope of the skill, and of its description. There's an inherent trade-off: go too broad, and it activates so often that it doesn't actually narrow the context — it might as well just be always loaded. Go too narrow, and it doesn't activate when it should, and doesn't add any value.

Skills actually have a third layer to them — three stages of activation:

  • Always: the name and description.
  • When relevant: the skill body text.
  • When extra stuff is needed: extra files.

Tools

Tools are what allow LLMs to interact with external systems.

Fundamentally, LLMs are designed to create text outputs. They are large language models — language is what they do. In order to interact with other systems, then, they need something with the ability to translate language into action.

This is where tools come in.

Tools are systems designed to accept text in a specific format and then execute some action based on that text. So, for example:

model generates 
{
  "tool": "get_weather",
  "input": { "city": "Seattle" }
}
tool returns 
{
  "temp_f": 58,
  "conditions": "light rain"
}
// this result is inserted back into the model's context
// before it continues generating

This means the tool framework is responsible for doing anything other than outputting text, and can be a great point of control for what the system can or cannot do. The model only ever generates the text. The tool is what actually goes out and does things, then returns information back to the model.

This doesn't come for free, however — tool descriptions, tool processing, and whatever the tool returns all become part of the context.

Agents

Placeholder — a model running the core loop with a goal, tools, and enough autonomy to decide its own next step. Subagents as isolated contexts for parallelism or a different tool scope; when spinning one up is worth the overhead.

MCPs

Placeholder — Model Context Protocol as a standard way to expose tools and resources to any compatible client, instead of writing bespoke integrations per agent. Tradeoffs versus a one-off tool.

Workflows

Placeholder — deterministic, multi-step chains versus a freeform agent loop: when a fixed sequence of steps is more reliable (and cheaper) than letting the model decide the order itself.

Middleware

Placeholder — hooks, guardrails, and pre/post-processing that wrap the model call: validation, logging, redaction, and policy enforcement that shouldn't live inside the prompt itself.

Context

As is hopefully clear now, context lies at the core of every LLM output. It's the piece that actually gets processed. It's what determines the available skills, tools, agents, and information. It's how costs are calculated. Ultimately, context is at the center of almost everything LLMs do.

Following this, managing context is of critical importance. Consequently, it gets an entire section in this repository.
